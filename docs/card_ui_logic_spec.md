# 単語カードUIロジック設計書

この文書は、大学受験英単語アプリの「フラッシュカードUI」に関する仕様を、Claude/ユーザー間の議論をもとにまとめたものです。実装担当（Claude Code）はこの文書を単一の正典として扱ってください。ここに書かれていない挙動を推測で実装しないでください。不明点は「未決定事項」セクションに列挙してあります。

対象範囲はカードUIロジックのみです。SRSスケジューリングアルゴリズム本体（FSRSの数式など）、語彙DB構築パイプライン、ホーム画面・弱点管理画面などは対象外です。

---

## 1. 基本データモデル

### 1.1 Word（見出し語）

```
Word
 ├─ word_id
 ├─ lemma            // 例: "suppose"
 ├─ pos_primary       // 表示用の主品詞（例: "動詞"）
 ├─ etymology         // 語源テキスト。1つのWordにつき1つ。senses[]全体で共通表示
 ├─ family_id          // Word Family（後述）でグルーピングするID。所属しない語はnull
 ├─ family_role        // "root" | "derived" | null（Word Familyに属する場合のみ）
 ├─ family_of_lemma    // derived の場合、親のlemma文字列（バッジ表示用。例: "suppose"）
 └─ senses[]           // 下記Sense参照
```

重要：`Word`は「1枚のフラッシュカード」に対応する単位です。Word Familyで別カード化された派生語（例: observation, supposition）は、それぞれ独立した`Word`エンティティであり、独立したSRS状態を持ちます。

### 1.2 Sense（語義・用法）

Wordの中に複数持てる配列。表面/裏面の描画とSRSはこの単位で管理します（語義ごとに独立した習熟度・次回復習日を持つ、Anki的な設計）。

```
Sense
 ├─ sense_id
 ├─ kind              // "meaning" | "pattern"　← 重要。挙動分岐に使う
 ├─ tag                // 裏面に表示する品詞ブラケット。例: "【他動】" "【熟】" "【接】" "【名】"
 ├─ pos_label          // 裏面上部に表示する広い分類ラベル。例: "動詞" "熟語" "接続詞" "名詞"
 ├─ meaning_ja         // 日本語の意味
 ├─ pattern_front      // kind="pattern"のときのみ使用。表面に出す構文の型そのもの。例: "be supposed to V"
 ├─ example_en         // 例文（英）。1つのみ。追加のコロケーションや類例は持たせない
 ├─ example_ja         // 例文（和訳）
 └─ user_state          // ユーザーごとのSRS状態（stability, due_date, repetitions等。詳細は本文書の対象外）
```

**kind の意味**
- `meaning`：その単語自体の意味（多義語の語義）。observeの「観察する/遵守する/祝う」、supposeの「思う/仮定する」がこれに該当。
- `pattern`：同じ見出し語に紐づく構文・慣用表現・語法。suppose の `be supposed to V`、`Supposing (that) ~` がこれに該当。**これらは別の見出し語カードにはしない**（詳細は4章）。

## 2. カードの状態遷移

カードは1つの`Word`につき次の3状態を持つUIコンポーネントとして実装します。

```
front（表面） → back（裏面） → [次のsenseがあれば front に戻る] → done（このWordの学習完了）
```

- 初期状態は必ず`front`
- `front`をタップ/クリックすると`back`に遷移（同一sense内での表裏反転）
- `back`でAgain/Hard/Good/Easyのいずれかを押すと、次の未処理senseがあれば`front`に戻り、なければ`done`（このWordの学習セッション終了）
- `done`後、Word Familyに派生語が控えている場合は次のWordのfrontへ自動的に接続する（4章参照）。控えていなければキュー上の次の見出し語へ進む（アプリ全体の出題ロジックの範囲であり本書対象外）

**重要**：`back`から`front`へ戻る際、senseが変わるたびに表面の表示内容を再計算します（後述の3章のルールに従う）。これは「一度裏返したら最後まで裏面のまま」という単純なフリップ動作ではなく、sense単位で表裏がリセットされる設計です。

## 3. 表面（front）の描画ルール

その日、そのWordについて出題対象となっているsenseの集合を「本日の対象sense」と呼びます（SRSスケジューラが決定するものであり、本書の対象外）。本日の対象senseが複数ある場合、1つのWordカードの中でsense単位のタブとして連続して出題します（3.4節参照）。

### 3.1 kind = "pattern" の場合

表面には常に `sense.pattern_front` をそのまま表示します。ヒントや除外表示は一切付与しません。表面の文字列自体がすでに一意な手がかりだからです。

例：表面 = `Supposing that ~`

### 3.2 kind = "meaning" の場合（除外ヒントなし）

対象Wordに「定着済み」と判定された同一Wordの他senseが存在しない場合、表面には`lemma`のみを表示します。

例：表面 = `suppose`

### 3.3 kind = "meaning" の場合（除外ヒントあり）

以下のいずれかに該当するsenseが1つ以上存在する場合、表面に除外ヒントを付与します。

- (a) 定着済み（マスタリー閾値を超えている。閾値の定義は「未決定事項」参照）と判定されたsense
- (b) 同じ復習セッション内で、このWordについて**すでに表示し終えた**sense（セッションの境界定義は「未決定事項」参照）

表示形式：
```
[lemma]
「[除外対象1のmeaning_ja]」「除外対象2のmeaning_ja」... 以外の意味は？
```

複数の除外対象がある場合は「」で個別に囲み、読点なしで連結して並べます（実装済みデモの表記に準拠：`「〜だと思う」「祝う」以外の意味は？`のような形）。

除外ヒントはUI上、lemma本体の下に控えめなチップ（アイコン+テキスト、`--text-secondary`系のトーン）として表示し、lemma本体より目立たせないこと。

### 3.4 同一Word内で複数senseが本日対象になっている場合の扱い

複数senseが同日対象になった場合、それらを1枚のWordカードの中でsense単位のタブとして連続出題します（ドットインジケーターで進捗を表示）。これによって「同じlemmaの表面が別々のタイミングで無関係に2回出る」事故を避けます。

タブが進むたびに3.1〜3.3のルールを毎回再評価してください（表示済みsenseの蓄積により、除外ヒントの内容は途中から増えていく）。

## 4. Word Family（派生語グループ）

### 4.1 定義

Word Familyは、**新規カード導入時の並び順を決めるグルーピング機能**です。習得判定によるロック/アンロックは一切行いません。

同一`family_id`を持つ複数の`Word`（例: suppose → supposition、observe → observation → observant）を、新規カードとしてキューに導入する際に、この順序で連続して導入します：

```
動詞 → 名詞 → 形容詞 → 副詞
```

（該当する品詞の派生語が存在しない場合はスキップし、次の品詞に進む。例：observantの後に自然な副詞形がなければ、そこでfamilyの導入は終わり、次の見出し語に移る）

### 4.2 各派生語カードの独立性

Word Familyに属する各`Word`は、通常のWordと全く同じ構造を持つ独立したカードです。それぞれが独自の`etymology`、独自の`senses[]`、独自のSRS状態を持ちます。1枚のカードに複数の派生語情報を詰め込むことは**しません**。

### 4.3 導入条件

**習得済みだから次の派生語が解放される、という条件分岐は実装しないでください。** 通常の新規カード導入ロジック（1日あたりの新規カード数の割り当てなど、本書対象外）の中で、family_idが同じ単語群は連続した並びとしてキューに投入されるだけです。

### 4.4 派生語バッジ

`family_role = "derived"` の`Word`のカードには、front・back両方の上部に小さなバッジを表示します。

```
[アイコン: git-branch] [family_of_lemma]の派生語を学習中
```

例：`suppose の派生語を学習中`

- rootの`Word`（例: suppose自体）にはこのバッジは表示しません
- Word Familyの「地図」「ロードマップ」「observe→observation→observantの遷移バー」のような常設ナビゲーション要素は**作らないでください**（過去の検討案として提示しましたが、ユーザーの明示的な指示により撤回済みです）

## 5. Word Familyかsense内wordバリエーションかの判定基準

`suppose`の`be supposed to V`のような表現を、Word Family（別カード）にするか、同一カード内の`kind: "pattern"`のsenseにするかの判定基準です。優先順位は以下の通り、上から適用してください。矛盾する結果が出た場合は基準1を常に優先します。

**基準1（最優先）：参照教材の構造をそのまま使う**
市販単語帳PDF（システム英単語、LEAP等）の解析結果において、見出し語ページ内の「派生語」「Word Family」見出しの下に掲載されている語 → Word Family（別カード）。「熟語」「イディオム」「語法」見出しの下に掲載されている表現 → 同一カード内の`kind: "pattern"` sense。

**基準2（教材に該当情報がない場合のフォールバック）：形態論ルール**
- 品詞を変える派生接尾辞（-tion, -ment, -ance/-ence, -able, -ful, -ive, -ous, -ize, -ly 等）が付与されている → Word Family
- 規則的な屈折変化（-ing, -ed, -s, -er/-est）、be動詞+分詞の慣用表現、-ing形の接続詞化など統語的なパターン → 同一カード内の`kind: "pattern"` sense

**基準3（最終フォールバック）：単独で意味が通じるか**
その表現だけを見て、元の単語を経由せず独立した概念として理解・使用できるか。できる（例: observation）→ Word Family。できない（例: Supposing that ~、単独では意味が完結しない）→ 同一カード内sense。

## 6. 裏面（back）の描画ルール

裏面は常に以下を表示します（sense種別によらず共通のレイアウト）。

- lemma（大きく表示）＋ `pos_label`（小さく右上寄せ）
- etymology（このWordに1つ。全senseで共通表示。アクセントカラーの帯）
- sense進捗インジケーター（「用法 n / 総数」テキスト＋ドット。本日対象sense数を分母にする。全senseの総数ではない）
- `tag`（ブラケット表記、アクセントカラー）＋ `meaning_ja`（大きく中央表示）
- 例文（英・和訳のセット、1つのみ。追加の類例・コロケーションの列挙は行わない）
- Again / Hard / Good / Easy の4ボタン（横並び、4等分）

`family_role = "derived"` の場合のみ、上部にバッジを追加表示（4.4節参照）。

## 7. 明示的に実装しないもの（却下済みの検討案）

以下は議論の過程で検討されたが、最終的にユーザーの指示により撤回・却下された機能です。実装しないでください。

- Word Familyの常設ロードマップ/地図バー（`observe → observation`のような遷移表示をカード裏面に常設すること）
- Word Family派生語の「定着後に解放」というアンロック条件
- 同じ構文枠を取る類似動詞の一覧表示（例: regard A as Bのカードに、see A as B / view A as Bを併記すること）
- 「紛らわしい構文」比較カードという新しいカード種別、およびそれを呼び出す専用メニュー
- ミニマルフレーズにおける複数コロケーションの列挙（1sense = 1例文の原則を破るもの）

## 9. 参考：実装済みデモの再現手順（Claude Code向け補足）

本文書の内容は、以下の一連のインタラクティブデモ（HTML/CSSモックアップ）で検証済みです。Swift実装時の状態遷移・表示ロジックの参考にしてください。

1. `observe`：3つの`kind: "meaning"` senseを持つ基本形（除外ヒントなし版）
2. `observe → observation`：Word Family遷移とバッジ表示
3. `suppose`：`kind: "meaning"`2つ + `kind: "pattern"`2つを1枚に統合した形
4. `suppose`（除外ヒント版）：定着済みsenseを踏まえた表面ヒント表示
5. `suppose`（本日対象3sense）→ `supposition`（Word Family）：本設計書の全ルールを統合したフルフロー

いずれもタップ→裏返し→評価→次sense、という状態遷移をJavaScriptのシンプルな状態管理（現在のword index, sense index, revealedフラグ）で実装しており、SwiftUIでは`enum CardPhase`のような列挙型とObservableな状態オブジェクトに素直に置き換えられる想定です。
