# 大学受験英単語アプリ 追補設計書（設定画面・デザインシステム・運用制約）

## 0. この文書の位置づけ

既存3文書（`プロジェクト概要.txt` / `card_ui_logic_spec.md` / `home_screen_design.md`）は作り込まれているが、これまでの議論の中で口頭・モックアップのみで確定し、**どの文書にも文字として書かれていない決定事項**がある。本書はそれらを補うための追補（アドオン）であり、既存3文書を置き換えるものではない。

**優先順位のルール**：内容が重複・矛盾する場合、以下の順で優先する。

1. `プロジェクト概要.txt`（プロダクトの思想・差別化戦略）
2. `card_ui_logic_spec.md`（カードUIロジックの単一の正典）
3. `home_screen_design.md`（起動〜ホーム画面まわりのUIロジック）
4. 本書（上記3文書の隙間を埋める補足）

本書に書かれている内容が既存3文書と矛盾する場合、それは記述漏れではなく本書側の誤りである可能性が高いので、実装前にユーザーへ確認すること。

## 1. 設定画面（未文書化だった画面）

`home_screen_design.md` 4〜5章はライブラリ・分析画面を詳細に定義しているが、設定画面は1章に「設定（既習教材/志望校/試験日の再編集はここから）」と一行あるのみで、構造が文書化されていなかった。モックアップで作成済みの構造を以下に正典化する。

### 1.1 画面構成

```
設定
 ├─ 学習プロフィール（セクション）
 │    ├─ 学年              → タップでオンボーディングStep3と同じ学年選択UIを再表示
 │    ├─ 既習教材           → タップでオンボーディングStep4と同じ複数選択UIを再表示。「◯件選択中」を右側に表示
 │    ├─ 志望校             → タップで志望校の追加・削除ができるUIへ。「◯校登録中」を右側に表示
 │    └─ 試験日             → タップで志望校ごとの試験日編集UIへ。「◯件未入力」のように未入力件数を右側に表示（home_screen_design.md 2.1章・エッジケース表と整合させる）
 ├─ プラン（セクション）
 │    └─ 志望校プラン        → 現在の課金状態（「加入中」/「未加入」）を右側に表示。タップで課金管理（購読状態の確認・解約導線）へ
 └─ アプリ設定（セクション）
      ├─ 通知（トグルスイッチ）→ 復習期限が来た語がある時のリマインド通知のON/OFF（OSの通知権限とは別に、アプリ内トグルとして持つ）
      └─ 学習データのエクスポート → タップでエクスポート実行（形式・対象範囲は3.1章のTBD参照）
```

### 1.2 学年・既習教材・志望校の変更が既存データに与える影響

- **学年の変更**：`home_screen_design.md` 2.1章のカウントダウン表示条件が再評価される（例：高2→高3に変更した瞬間、共通テストカウントダウンの表示が始まる）。すでに学習済みのUserWordStateには影響しない。
- **既習教材の変更（追加）**：追加した教材由来の語彙が新たに「既習候補」としてインポートされる。すでに学習履歴があるWordには影響しない（上書きしない。プロジェクト概要4章の「既習候補は初期値に過ぎない」という原則を維持する）。
- **既習教材の変更（削除）**：**未決定**（3.1章のTBD参照）。既にインポート済みの既習候補を取り消すのか、それとも一度インポートされたものは変更後も保持するのか、実装前に決める必要がある。
- **志望校の削除**：削除した学校が「固有語彙」として持っていた単語（`required_for_schools`が他校を含まない語）は、その語のUserWordStateごと削除するのか、学習履歴だけは残すのかは**未決定**（3.1章のTBD参照）。

## 2. ビジュアルデザインシステム

これまでのモックアップ制作で実質的に固まった見た目のルールを、Claude Codeが実装時に迷わないよう明文化する。

### 2.1 採用が確定している方向性（ダークテーマ・フィルカード）

このプロジェクトの提供画像（`suppose`/`observe`のカード、ホーム画面、ライブラリ、設定、分析の各画面）に写っている見た目が、**最終的に採用が確定しているデザイン**である。

- **背景**：ダークテーマ固定（ライトテーマの対応は現時点でスコープ外。必要なら別途指示する）
- **カードコンポーネント**：塗りつぶしのある面（surfaceカラー）＋細いヘアライン境界線（0.5px相当）＋角丸（12px程度）。ドロップシャドウのような重い装飾は使わない、フラットな見た目
- **テキストの階調**：本文用（primary）、補足用（secondary）、さらに薄いラベル用（muted）、アクセント（accent、青系）の最低4段階の濃淡を使い分ける
- **アクセントカラー**：青系1色に統一。進捗バー、選択中のタブ、リンク的なテキスト、ボトムナビの選択中アイコンなど、「今どこにいるか」を示す用途に限定して使う
- **SRS評価ボタンの配色（固定）**：Again＝赤系、Hard＝オレンジ/黄系、Good＝緑系、Easy＝青系。この4色の対応関係は`card_ui_logic_spec.md`のデモ全体で一貫しており、変更しない
- **アイコン**：線画スタイル（Tabler Icons相当）のアウトラインアイコンを使用。塗りつぶしアイコンは使わない
- **ボトムナビゲーション**：ホーム / ライブラリ / 分析 / 設定 の4タブで固定。アイコン＋ラベルの縦積み、選択中のタブのみアクセントカラーで強調

### 2.2 過去に検討され、不採用になった方向性（実装しないこと）

開発初期に、上記とは異なる配色・レイアウトの方向性（暖色系の背景色`#F1EFE8`・`#2C2C2A`、カードを使わずヘアラインのみで区切る、進捗をリング型ではなく数字中心のタイポグラフィで見せる、ストリークをテキストのみで表現する、ボタンをアウトラインのみにする等）を試作した。

**これは不採用となった過去の検討案であり、現在の正典ではない。** Claude Codeが過去のセッションログやエクスポートファイルにこの配色案を見つけても、実装に使わないこと。現在の正典は2.1節のダークテーマ・フィルカード方式のみである。

### 2.3 タイポグラフィ・具体的なカラーコード

フォントファミリー・具体的なHEXカラーコードは、この設計セッションでは確定していない。**未決定事項**として3.1章に記載する（iOS標準のシステムフォント〈San Francisco〉を前提にする分には問題ないが、独自フォントを使うかは未確認）。

## 4. 過去問データ処理パイプラインに関する運用原則

`プロジェクト概要.txt` 32〜35章に「過去問を教師データとして使う」という思想は書かれているが、**Claude Codeが実際にどう処理すべきか**という実務上の制約は別の会話でのみ確定しており、どの文書にも書かれていなかった。実装時の事故（著作権侵害・処理不能）を防ぐため、ここに明文化する。

### 4.1 「一括で読み込む」という発想を禁止する

過去問PDFを大学・学部×20年分など大量に扱う際、**Claude Codeが全ファイルの内容を一度にコンテキストへ読み込もうとしてはいけない**。正しい設計は以下の役割分担。

- **機械的な抽出・集計作業（AIの判断不要）**：PDFからのテキスト抽出、単語・熟語のトークナイズ、大学・学部・年度ごとの頻度カウントは、すべてPythonスクリプトのループ処理で行う。1ファイルずつ順に処理すれば、合計サイズが数GB〜数十GBでも問題にならない
- **AIの判断が必要な作業**：重要度スコアリングの重み付け、多義語の語義整理、基礎語ペナルティの調整など。この作業に渡すのは生のPDF本文ではなく、**既に集計済みの軽量な構造化データ**（単語＋頻度＋文脈例など）に限定する

### 4.2 著作権上の制約（実装時に必ず守ること）

- 過去問PDFの**本文（長文パッセージ・設問文）をそのままアプリ内DBに保存・配布してはならない**
- アプリのDBに永続化してよいのは、抽出後の**統計データ（どの単語がどの大学・年度で何回出現したか、という事実・数値データ）のみ**
- PDF本文はテキスト抽出時に一時的にしか扱わず、集計が終わった時点で本文データは破棄する（一時ファイルとして扱い、DBへの永続保存はしない）

### 4.3 データの受け渡し方法（今回の運用）

過去問データはユーザーがGoogleドライブにまとめ、URLを共有する運用となっている。Claude Codeがこれをダウンロードする際の注意点：

- Googleドライブの「リンクを知っている全員が閲覧可」の共有URLは、そのままでは直接ダウンロードできるURLではない（ブラウザ表示用のページになる）。大容量ファイルではウイルススキャン確認ページが挟まることもある
- `gdown`（Pythonパッケージ）を使うと、上記の確認画面を自動的に回避してダウンロードできる。ファイル数が多い場合はレート制限を避けるため、可能であれば1つのzipにまとめておくことが望ましい

### 4.4 iOSアプリのビルド・App Store提出に関する制約

開発環境としてiPad＋Claude Codeのクラウドセッションを使う運用のため、以下は開発当初から認識しておくべき制約として明記する。

- データパイプラインの構築・検証まではクラウド環境（Mac不要）で完結できる
- しかし、**実際にiOSアプリをビルドしてApp Storeへ提出する工程には、最終的にXcode（＝Mac環境）が必要**になる
- 対応策の候補：クラウドMacサービス（CI/CD、ビルド代行）を利用してビルド・申請工程だけそこで行う。この点は開発後半で改めて選定する
